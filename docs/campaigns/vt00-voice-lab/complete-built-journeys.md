# C4 complete built-Sophia journeys

Status: `PROTOCOL DEFINED — EXACT DEPLOYMENT AND LIVE EVIDENCE PENDING`

The twenty-journey requirement is a separate pre-canary collection phase, not
twenty injected operations in one process and not a local development test.
After all non-live prerequisites pass on the exact built C4 candidate, use the
runbook's ordered opening and reverse-order closing procedure for a bounded
window of at most twenty sequential V-F01 starts through installed Lab tools.
The journey and five-canary gates may be pending during this journey window;
no other pending prerequisite is waived. No official P01 or suite runs here.

For each journey:

1. Record exact product, dependency, harness and installed protocol identities.
   Start a fresh run using ordinary authenticated product/controller behavior.
   Require the acquired browser boot/execution identity to differ from every
   previously counted journey; worker identity alone is not fresh-process proof.
2. Await current-owner product readiness, not merely an old setup event or
   successful start admission. Missing readiness ends this attempt as failed.
3. Speak one neutral synthetic prompt, then require joined input PCM,
   transcription, accepted canonical turn and realized assistant playback.
4. Choose a bounded second utterance from that canonical observation. Require
   the same complete input/output chain for the response. Do not overlap turns,
   seed browser state, use DOM activation, or substitute text for speech.
5. End through the installed tool, observe its terminal operation, inspect and
   export the durable evidence. Require finalization, exact owned-resource
   settlement, process close and evidence integrity before another run starts.
6. Append the immutable manifest reference/hash, run identity, distinct process
   binding and independently classified harness/product outcomes to the journey
   inventory. A required missing join is not a pass. Preserve failed attempts.

The first harness, authorization, capture or cleanup ambiguity ends the window;
close gates in strict reverse order and diagnose. A later window has a new
explicit start-count bound and must obey the existing per-run/concurrency/spend
limits. Already qualified journeys count only for the same unchanged exact
candidate; a code/protocol change requires requalification. Twenty complete
journeys do not satisfy the separate five consecutive deployed canaries or the
fresh installed-root P01. Product failures remain governed by the inherited
complete-evidence/downstream-owner rule; missing harness proof cannot pass.

After twenty qualify, close and attest this window before opening the separate
five-canary window. The historical acceptance exception remains disclosed and
does not waive settlement for any of these new runs. This protocol is not itself
execution evidence and cannot set the journey checkpoint to passed.
