# Common Pitfalls

Date created: 2026-05-17

## Sophia Voice Realtime Migration

- Do not treat `voice/adapters/base.py` `BackendAdapter` as the realtime provider seam. It is a text-backend bridge for finalized user turns; native realtime providers need session, audio, tool-call, cancellation, and lifecycle events.
- Do not emit provider-native event names to the browser. Frontend voice consumers in `frontend/src/app/hooks/useStreamVoiceSession.ts` understand the public `sophia.*` envelope, not OpenAI, Gemini, Deepgram, Cartesia, or Vision Agents wire names.
- Do not treat voice provider disconnect as memory recap finalization. Stream/Gemini/OpenAI disconnect endpoints close transport sessions; recap persistence and Mem0 extraction belong to the Sophia session finalizer or an explicitly documented offline finalization path.
- Do not add recap finalization to hook cleanup, mic stop, preconnect cleanup, previous-session cleanup, or provider disconnect by default. In Phase 12.6E, intentional voice end finalizes through Sophia `end-session` first, then calls cleanup-only `stopVoiceTransport()`.
- Do not overfit the provider-neutral contract to OpenAI before Gemini exists. Keep capability flags and event names semantic enough for both provider-owned audio and audio-lifecycle-driven turn events.
- Do not switch the active runtime while doing architecture-only plumbing. Phase 1 adds `voice.realtime` as an inactive contract layer; the current cascade in `voice/server.py` stays default.
- Do not confuse the legacy cascade compatibility bridge with a production runtime replacement. It proves the current cascade can be represented as `ProviderEvent`; it does not route live sessions through `voice.realtime`.
- Do not let compatibility code re-emit `sophia.*` directly. Legacy bridge code must stop at `ProviderEvent` so `SophiaEventNormalizer` remains the single public event boundary.
- Do not infer provider-neutral abstractions from Deepgram or Cartesia quirks. Preserve legacy component details as metadata or provider hints, then map future providers from their verified capabilities.
- Do not treat existing legacy event order as accidental. Frontend state and tests depend on user transcript, turn phase, partial/final transcript, artifact, builder task, and diagnostic ordering.
- Guard duplicate public turn phases. Native providers may emit both response lifecycle and audio lifecycle events; the normalizer must avoid duplicate `agent_started` or `agent_ended` frontend stage flips.
- Keep partial user transcripts internal unless the frontend contract is deliberately expanded. The current browser path treats `sophia.user_transcript` as the finalized visible user turn.
- Do not confuse shadow parity output with frontend output. Shadow parity may generate expected `sophia.*` envelopes internally, but only the existing live emitter may publish public events.
- Do not treat `openai_realtime` or `gemini_live` as production defaults. Phase 6 makes them experimental active runtimes only when `SOPHIA_VOICE_RUNTIME_MODE=<provider>`, `SOPHIA_VOICE_EXPERIMENTAL_RUNTIME_ENABLED=true`, and the matching provider adapter flag are all set.
- Do not call the Stream/Vision Agents `/calls/{call_id}/sessions` route when an experimental provider runtime is selected. Phase 7 exposes provider modes only through `/dogfood/realtime/sessions`; the Stream route is legacy-cascade-only and must fail with a conflict instead of silently falling back.
- Do not treat Phase 7 dogfood SSE as raw provider telemetry. `/dogfood/realtime/sessions/{session_id}/provider-events` may ingest provider wire payloads internally, but `/dogfood/realtime/sessions/{session_id}/events` must stream only normalized `sophia.*` envelopes from `SophiaEventNormalizer`.
- Do not claim OpenAI/Gemini browser audio is complete because the dogfood event pump exists. OpenAI still needs WebRTC media routing for browser/mobile audio, and Gemini still needs a Live API WebSocket/audio bridge before either replaces Stream/Vision Agents.
- Do not claim Phase 8A is successful just because the browser WebRTC peer connection reaches OpenAI. The backend sideband must attach to the `rtc_*` call id and normalized `sophia.*` SSE must flow through `OpenAIRealtimeEventMapper` plus `SophiaEventNormalizer`.
- Do not assume a transport-complete dogfood path is human-friendly by default. A working helper plus backend sideband is still too low-level for product dogfooding if Edward has to replay WebRTC, sideband, and SSE steps manually.
- Do not expose `OPENAI_API_KEY` to the browser. Phase 8A browser code uses only the ephemeral `client_secret.value` minted by `POST /dogfood/realtime/openai/browser-sessions`; the trusted backend uses the standard key for client-secret minting and sideband WebSocket attach.
- Do not assume a backend-minted OpenAI client secret proves the browser transport is allowed. The direct browser `POST https://api.openai.com/v1/realtime/calls` still needs the frontend CSP `connect-src` to allow `https://api.openai.com`.
- Do not read `Failed to fetch` on `/debug/realtime/openai` as an automatic provider-auth failure. Check the browser console and Network panel for a CSP block on `https://api.openai.com/v1/realtime/calls` before debugging sideband or model settings.
- Do not parse OpenAI call ids from arbitrary strings. Use the `rtc_*` id from the official WebRTC `Location` header returned by `POST /v1/realtime/calls`, and reject missing or malformed ids before opening a sideband URL.
- Do not keep tuning OpenAI sideband retry timing once the browser has supplied ICE-connected/WebRTC-ready evidence and OpenAI still returns 404 for the documented `wss://api.openai.com/v1/realtime?call_id=rtc_...` URL.
- Do not treat sideband 404 after confirmed WebRTC readiness as another vague runtime delay bug. Capture the raw `Location`, extracted `rtc_*`, SDP status, requested model, request id, and run the isolated sideband probe before changing architecture.
- Do not tear down a live OpenAI provider audio session just because the backend sideband attach fails during dogfood. If browser WebRTC is already connected, keep the call alive in explicit degraded audio-only mode so attach can be retried against the same active `rtc_*`.
- Do not treat an isolated sideband probe run after the browser session has already disconnected as proof of active-call provider behavior. A post-teardown 404 only proves the call is gone.
- Do not conclude provider incompatibility from sideband 404s until you have retried sideband attach against the still-live `rtc_*` from the debug page and captured the resulting request id, raw error text, and current WebRTC readiness evidence.
- Do not assume `gpt-realtime-2` is or is not the sideband cause. Test the documented baseline `gpt-realtime` model under the same flow and compare probe results.
- Do not splice OpenAI browser WebRTC dogfood into `useStreamVoiceSession` or `/voice/connect`. Phase 8A uses separate `/voice/dogfood/openai/*` proxy routes and `frontend/src/app/lib/openai-browser-webrtc-dogfood.ts` so production voice remains `legacy_cascade`.
- Do not make Edward reimplement the low-level OpenAI browser sequence in ad hoc scripts when `frontend/src/app/lib/openai-browser-webrtc-dogfood.ts` already owns it. Wrap that helper in an explicit internal UI instead of cloning the sequence again.
- Do not merge internal OpenAI dogfood UI into the production Stream voice experience. Keep dogfood pages under explicit debug/internal routes so experimental runtime work cannot be mistaken for the default voice path.
- Do not show raw OpenAI provider traffic in internal event logs. Even dogfood UIs should subscribe to normalized `sophia.*` SSE and keep provider-native event names behind the sideband and adapter boundary.
- Do not proxy a backend `204 No Content` disconnect through a Next route handler with an empty-string body. Use a null body for empty responses or a successful OpenAI dogfood cleanup can surface as a frontend 500.
- Do not require a fully attached sideband before allowing OpenAI dogfood cleanup. Failed-connect cleanup must be safe and idempotent when the browser session started but the direct WebRTC call or sideband attach never completed.
- Do not claim Gemini has an OpenAI-style backend sideband. Phase 8B uses browser-owned client-to-server Live WebSocket access with an ephemeral auth token plus an authenticated backend relay for normalized observation.
- Do not expose `GOOGLE_API_KEY` or `GEMINI_API_KEY` to the browser. Phase 8B browser code uses only the ephemeral token minted by `POST /dogfood/realtime/gemini/browser-sessions`; the trusted backend uses the standard key for auth-token minting only.
- Do not relay Gemini client input messages back to the backend. The Phase 8B relay accepts documented Gemini Live server messages such as `setupComplete`, `serverContent`, `toolCall`, `toolCallCancellation`, `goAway`, `sessionResumptionUpdate`, `usageMetadata`, and `error`; browser microphone `realtimeInput` stays on the direct WebSocket.
- Do not forward Gemini WebSocket lifecycle noise or empty provider frames into the backend relay. Browser `open` / `close` / `error` events are transport state, not provider messages.
- Do not treat a `422 Gemini browser relay event cannot be empty` failure after successful browser-session creation as a provider-auth problem. It means the browser helper forwarded `{}` or another no-op frame instead of a real Gemini server message.
- Do not treat every empty-looking nested object as invalid. Gemini Live `setupComplete: {}` is an official zero-field server message and is load-bearing for the browser helper's setup gate.
- Do not let transport guardrails suppress officially zero-field protocol events. Empty strings, plain `{}`, and empty `serverContent: {}` should be filtered, but `setupComplete: {}` must update local setup state and remain relayable for backend observation.
- Do not send Gemini mic audio before `setupComplete`. The connector must send `setup` first, wait for `setupComplete`, then stream base64 PCM16 16 kHz audio.
- Do not treat Gemini output audio as compressed browser-native audio. Official Gemini Live output audio is raw signed PCM16 little-endian at 24 kHz, usually carried in `serverContent.modelTurn.parts[].inlineData` with an `audio/pcm` MIME type.
- Do not start every Gemini output PCM chunk at the current Web Audio time. Streaming chunks need ordered sequential scheduling; otherwise adjacent buffers can overlap and sound like multiple voices or languages stacked together.
- Do not treat every Gemini `input_audio_frame_sent` diagnostic as a confirmed barge-in. Phase 12.6D-C makes raw mic frames candidate evidence only; they must never arm stale-output suppression by count/duration alone. Confirm only from provider interruption, explicit manual/local interrupt, or conservative provider input transcription with real text after assistant output begins. Sustained speech confirmation needs actual confidence/amplitude evidence; raw frame count is not enough.
- Do not equate a single Gemini relay `Failed to fetch` with provider session death. Distinguish provider transport state from observability relay state: Gemini WSS and public SSE can remain connected while one relay POST is degraded.
- Do not use fetch `keepalive` for normal Gemini provider-event relay traffic. Keepalive belongs on disconnect/teardown calls; streaming relay payloads, especially audio-bearing `serverContent`, need normal fetch behavior and diagnostics.
- Do not infer that browser-owned Gemini Live means tools execute in the browser. The browser owns microphone/audio and the provider WSS; Sophia business logic and dogfood tools execute on the backend relay path.
- Do not forget that Live API function calling requires manual `toolResponse` handling. The backend returns a Gemini-compatible payload, but the browser must send it over the existing WSS; Google does not auto-run or auto-return tool results for this path.
- Do not leave diagnostic probe tools in a product-facing or real-provider session setup. Temporary transport probes are useful for one migration phase, but Gemini Live tool declarations should promote only already-existing Sophia backend tools.
- Do not turn Coreview artifact review into continuous watching, screen capture, camera capture, or browser-tab capture. The current product path sends one artifact-scoped canvas still frame after the user clicks Review with Sophia; exact words and numbers must use `read_artifact_text` or the trusted text sideband, never OCR, and telemetry must keep `rawFrameExcluded`, `rawProviderPayloadExcluded`, and `rawArtifactTextExcluded` true.
- Do not treat a successful Gemini tool-response loop as proof of Sophia capability coverage. A loop can prove transport mechanics while still using a fake tool; validate at least one real existing tool, starting with `emit_artifact`.
- Do not compare OpenAI and Gemini provider quality before confirming they received Sophia-equivalent prompt sources. Gemini's browser Live setup must use the canonical Sophia instruction assembly, not a compact Gemini-only persona prompt.
- Do not assume canonical Sophia prompt files are enough for Gemini memory parity. Legacy cascade voice reaches `UserIdentityMiddleware`, `SessionStateMiddleware`, and `Mem0MemoryMiddleware` through DeerFlow; Gemini Live setup must inject trusted user context before the first setup message because Live sessions do not accept later prompt updates.
- Do not treat Phase 12.5A context parity as a mandate to copy the full DeerFlow/Sophia middleware chain into native realtime. Classify each capability first: setup context, bounded setup context, on-demand tool, sideband/asynchronous, backend/UI-only, outside realtime, harmful, or unknown/needs tests.
- Do not chase full cascade parity by dumping the full identity file, full handoff, full Mem0 search space, full tone guidance, all ritual/context files, and every tool contract into Gemini or GPT Realtime setup. Bounded setup context plus tools is the intended path.
- Do not block native realtime speech on per-turn Mem0 retrieval or middleware prompt assembly unless a later phase proves the latency and behavior trade-off is worth it. Memory writeback and recap work should stay sideband/asynchronous by default.
- Do not put artifact, builder, tone, session-goal, or memory-review bookkeeping into spoken realtime prompt text. Keep product state in structured tool calls, public `sophia.*` events, and UI surfaces.
- Do not assume GPT Realtime automatically fixes Gemini's context-risk profile. OpenAI may allow session updates and semantic VAD, but full prompt/memory/tool expansion still needs the same staged evidence and privacy boundaries.
- Do not pass user profile or memory context to Gemini from model/tool arguments. Use the authenticated session user id from `/voice/connect` or the internal dogfood request; model-supplied ids remain diagnostic hints only.
- Do not include raw memory text in setup diagnostics or telemetry. The prompt block can contain bounded context for the authenticated user, but public diagnostics should stay to booleans, counts, categories, character lengths, and status.
- Do not treat GPT Realtime's default server-side conversation model as a Gemini Live guarantee. Gemini tool calls, tool responses, public `sophia.*` events, and setup context need provider-specific proof before they are used as next-turn model-visible memory.
- Do not implement `consult_skill` in realtime voice mode. Phase 12.6A bakes the eight fixed emotional skills into the cached prompt prefix; `skill_loaded` is self-observed mode, not a skill tool-call record.
- Do not put voice skill slow-state values in the cached prompt prefix. Phase 12.6C appends `### Voice Skill State` at setup time after trusted user context; it carries session count, trust, recurring patterns, prior tone band, and `challenging_growth` gating with conservative defaults.
- Do not bundle `retrieve_memories`, ritual/context tools, time tools, and `wait_for_user` into one realtime phase. Start with the smallest auditable surface, especially query-only `retrieve_memories`, before adding more model-choice tools.
- Do not change artifact schemas, VAD/activity settings, provider defaults, builder storage/UI, or Gemini/GPT routing during the realtime memory-tool phase. Those are separate migrations with different failure modes.
- Do not reintroduce the older MCP/server-url, session-log, or shared-view scope into Phase 12.5B-B unless Davide explicitly reopens it. The current voice specs choose in-process function tools and artifact traces for the voice hot path.
- Do not invent new Gemini-specific tools when an existing Sophia backend capability already covers the validation target. Derive declarations from a dependency-safe backend contract and execute the backend-owned tool contract on the relay path.
- Do not import backend tool implementation modules from realtime transport layers solely to derive provider tool declarations. LangChain-decorated tool modules can carry backend-only dependencies such as `langchain_core` that are intentionally absent from the voice runtime.
- Do not expose realtime `retrieve_memories` as anything except query-only. The model must never provide `user_id`, categories, raw filters, or provider config; bind identity from the authenticated session and keep category weighting internal.
- Do not duplicate raw memory text in realtime diagnostics. The memory text belongs in the bounded tool result only; telemetry should contain status, count, latency, query length, categories, and text lengths.
- Do not let browser-side Gemini diagnostics reintroduce raw memory text after backend redaction. The actual `toolResponse` sent to Gemini may contain bounded memory text, but `gemini-tool-loop-diagnostic` events and telemetry exports must keep only safe attribution fields such as fingerprints, counts, categories, lengths, and exclusion flags.
- Do not classify a realtime recall failure from status/count alone. Preserve safe query/result attribution (`query_fingerprint`, `result_fingerprints`, term-match counts, `has_results`) so the next smoke can distinguish missing memory, `no_results`, query mismatch, and model failure to use a relevant returned memory.
- Do not treat text companion checkpointer context as the realtime context model. Native realtime should use seed plus provider conversation plus tools, not per-turn LangGraph message/state replay.
- Do not assume a prior `sophia.artifact` public event is visible to Gemini or GPT on the next turn. Public artifact events are UI/telemetry state; provider-visible artifact orientation must come from function-call/tool-output conversation mechanics or an explicit compact bridge.
- Do not inject full artifact history into realtime prompts. If artifact orientation is needed, use only the latest valid companion artifact summary, keep it internal/non-spoken, and make the current user turn outrank it.
- Do not manually re-inject the previous artifact every realtime turn until a provider-specific proof harness shows native tool/function context is insufficient.
- Do not confuse artifact orientation with durable memory. The artifact is current-session meta-assessment; Mem0 is durable memory; handoff is cross-session summary; current transcript is immediate intent.
- Do not design reconnect/reseed payloads as full transcript or checkpointer dumps. Reseed should be compact: preferred name, bounded identity/handoff, top memories, latest artifact summary, active builder summary, short session recap, and ambient time.
- Do not treat setup-time preferred-name continuity as proof that realtime Mem0 is reachable. Gemini setup can read identity/handoff files even when the Mem0 SDK or `MEM0_API_KEY` is missing from the voice runtime.
- Do not collapse realtime memory failures into a generic unavailable state. Distinguish missing config/dependencies (`unavailable`), provider-reachable zero matches (`no_results`), and provider search exceptions (`error`), and include a safe `provider_reason` in diagnostics.
- Do not make the voice runtime depend on backend-only Mem0 SDK packages just to execute read-only realtime recall. Keep the shared Mem0 wrapper dependency-tolerant and use the SDK path when available or the REST fallback when only `MEM0_API_KEY` plus `httpx` are present.
- Do not assume one broad realtime memory search covers later specific recall questions. A later question such as `do you remember my favorite childhood movie?` should trigger a fresh focused `retrieve_memories(query)` call unless that exact fact was already retrieved or spoken.
- Do not blur setup context, stored memory, and current-session facts. Identity/handoff/profile setup can answer some questions, but only retrieved memories or explicit stored-memory seed items justify saying `I remember`.
- Do not treat `no_results` as broken memory or unavailable memory. It means the provider was reachable and found no relevant stored match; say `I don't have that stored` and ask or guess honestly if needed.
- Do not treat `unavailable` or `error` as proof the memory does not exist. Say memory retrieval cannot be checked right now and continue from setup/current-session context.
- Do not say `I knew it`, `I remembered that`, or `I had that stored` after the user reveals an answer that was guessed or hinted. Treat it as current-session knowledge until offline writeback persists it.
- Do not promise durable memory for a fact first learned in the current live session. Say it is held for this session only unless the offline memory pipeline later persists it.
- Do not let existing-tool promotion erase dependency boundaries. A real Sophia tool can be promoted to Gemini only through a lightweight declaration contract plus backend-owned execution, not by making the voice runtime own backend harness dependencies.
- Do not advertise Gemini builder/lifecycle tool names unless backend execution is wired in the same phase. Setup declarations and relay execution must move together for `start_builder_task`, `check_async_task`, `update_async_task`, `cancel_async_task`, and `list_async_tasks`.
- Do not import `deepagents`, `langgraph_sdk`, `langchain_core`, or the LangChain-decorated `start_builder_task` implementation into `voice.realtime` just to declare Gemini builder tools. Use a dependency-safe contract plus backend-owned LangGraph execution.
- Do not trust a Gemini-supplied `user_id` tool argument for builder launches. The authenticated dogfood session user id is the source of truth; model-provided user ids are diagnostic hints only.
- Do not route Gemini builder lifecycle calls through older task-management endpoints that are not backed by the current deepagents `async_tasks` state. The dogfood relay must track launched builder thread ids and use the LangGraph lifecycle for status/update/cancel/list.
- Do not assume providers will respect builder task-id sequencing unless declarations and prompt guidance say it explicitly. Lifecycle tools must only use real tracked ids returned by `start_builder_task` or `list_async_tasks` in the current trusted session; invented ids must fail closed.
- Do not classify an unknown builder lifecycle task id as a transport failure. It is a valid tool execution rejection when Gemini WSS and public SSE remain connected and the relay returns a model-recoverable `toolResponse` with `ok:false`.
- Do not let pseudo tool syntax leak into spoken text or assistant transcript. Raw strings such as `try{emit_artifact{...}}`, JSON-ish tool calls, or `check_async_task({...})` are model text leakage, not structured tool use.
- Do not read a `500` before Gemini auth/session setup as a provider issue by default. A local declaration import failure can crash `/dogfood/realtime/gemini/browser-sessions` before Google is contacted.
- Do not collapse tool declaration, backend execution, and client send-back into one responsibility. Gemini setup declares tools, the backend validates/executes `toolCall`, and the browser sends the returned `toolResponse` payload.
- Do not confuse normalized observability events with backend tool execution. A `sophia.turn_diagnostic` can prove the backend observed/executed a tool call, but Gemini only resumes after the browser sends the actual `toolResponse` client message.
- Do not derive important Gemini debug state only from a capped recent diagnostic log. `Last start task id` and trusted tracked task ids must survive later lifecycle diagnostics that push the original `start_builder_task` event out of the visible list.
- Do not promote a rejected or model-invented lifecycle id into trusted tracked task state. Show the rejected id in the rejection fields, but populate tracked ids only from successful/trusted backend responses or returned `tracked_task_ids`/task lists.
- Do not treat fast builder completion as proof that `update_async_task` or `cancel_async_task` is broken. Manual live smokes may need a longer-running task so update/cancel happens before the builder reaches a terminal status.
- Do not infer production cutover readiness from `/debug/realtime/gemini` success alone. Dogfood success must be mapped against `/voice/connect`, `useStreamVoiceSession`, warmup, teardown, telemetry, interruption behavior, and fallback/rollback parity.
- Do not promote Gemini into the production `/voice/connect` route with only `SOPHIA_VOICE_RUNTIME_MODE=gemini_live`. Phase 12.0 also requires `SOPHIA_VOICE_GEMINI_PRODUCTION_ROUTE_ENABLED=true`; otherwise the route must fail closed and tell the operator how to roll back.
- Do not silently fall back to Stream when Gemini production route configuration is broken after Gemini was explicitly selected. Missing promotion flag or provider credentials should be a clear startup/connect failure, not an accidental legacy session.
- Do not allow legacy auto-preconnect to open a Gemini Live browser session before the user starts voice. Production Gemini rejects `preconnect: true`; real browser microphone/WebSocket startup happens only from the user-initiated connect flow.
- Do not point production browser code at `/debug/realtime/gemini` or `/voice/dogfood/gemini/*` when testing the route candidate. The production candidate returns authenticated aliases under `/api/sophia/voice/gemini/*` from the normal `/voice/connect` response.
- Do not splice Gemini browser Live dogfood directly into production surfaces. Phase 8B used separate `/voice/dogfood/gemini/*` proxy routes; Phase 12.0 production integration must go through `/voice/connect` runtime selection, production aliases, and the explicit promotion flag while keeping `legacy_cascade` as default.
- Do not infer the Session telemetry runtime from frontend env flags. Phase 12.1 runtime identity comes from the actual `/voice/connect` selection and is carried through `useStreamVoiceSession` into the panel.
- Do not show legacy Stream/Vision Agents cascade latency cards as universal voice metrics. In Gemini Live sessions, Stream join, remote participants, raw backend-done, and TTS/playback bottleneck labels are not applicable unless the production path explicitly emits equivalent provider-neutral evidence.
- Do not drop Gemini helper callback state when moving from debug routes to the production Session UI. Relay status, WSS stage, provider event count, output audio, and tool-loop diagnostics are the truthful Gemini production telemetry surface.
- Do not assume `partialReply` is enough for real Session transcript rendering. The production `/session` transcript and voice captions render from Session messages, so normalized assistant partial transcripts must also flow through the assistant-message bridge.
- Do not feed live voice `sophia.artifact` payloads directly into `mergeRitualArtifacts`. Route them through the shared artifact parser first so companion artifacts are canonicalized and nested `{ artifact: ... }`, `{ payload: ... }`, or double `{ data: ... }` envelopes can render visibly.
- Do not treat stringified null values as real artifact content. `reflection: "null"`, `"none"`, `"undefined"`, `"n/a"`, and empty strings must be normalized to absent before UI status or rendering marks reflection as ready.
- Do not merge builder document artifacts into companion ritual artifacts. Companion `emit_artifact` payloads update the Presence/Artifacts panels; builder outputs stay on the builder artifact path.
- Do not assume Gemini transport plumbing is product-dogfood ready just because the helper and relay exist. Edward still needs an internal page that wraps the helper and exposes connection, setup, relay, and SSE state without manual browser scripting.
- Do not make Edward replay the low-level Gemini browser session, WebSocket, and relay steps by hand when `frontend/src/app/lib/gemini-browser-live-websocket-dogfood.ts` already owns that sequence. Put a debug page on top of the helper instead of cloning the transport again.
- Do not merge Gemini dogfood UI into the production Stream voice surface. Keep internal browser testing under explicit debug routes such as `/debug/realtime/gemini`.
- Do not show raw Gemini provider event names in the public event log. Internal pages should subscribe to normalized `sophia.*` SSE only, even while the browser relay posts documented Gemini server messages underneath.
- Do not describe Gemini browser dogfood as an OpenAI-style sideband path. Gemini browser testing is direct browser-owned WSS plus authenticated backend relay for normalized observation.
- Do not start experimental OpenAI/Gemini dogfood without provider credentials. OpenAI requires `OPENAI_API_KEY`; Gemini accepts `GOOGLE_API_KEY` or `GEMINI_API_KEY`.
- Do not compare OpenAI and Gemini dogfood runs with different prompts, different scenario order, or wildly different microphone/network conditions. Phase 9 comparisons only count when the manual scenario matrix is repeatable.
- Do not compare providers from memory. Record the run in the structured launcher or template while the evidence is still in front of you.
- Do not judge a provider before it has gone through the same S01-S15 matrix as its counterpart. A partial pass is not a comparative result.
- Do not leave manual dogfood notes in the browser and promise to reconstruct them later. Export the JSON run record and copy the summary immediately after the run.
- Do not mistake provider-page availability for evaluation evidence. A connectable transport page is necessary, but it does not replace a scored comparative run record.
- Do not treat a strong subjective voice demo as provider readiness. Event stream correctness, interruption handling, artifact presence, session close/recovery, and sideband/relay health are part of the score.
- Do not write dogfood conclusions without a run record. Manual impressions are invalid unless scenario ids, latency notes, transcript notes, `sophia.*` event health, and observed failures are captured.
- Do not collapse OpenAI sideband health and Gemini relay health into one transport score. OpenAI must attach the backend sideband to the `rtc_*` call id; Gemini must relay browser-captured server messages after `setupComplete`.
- Do not promote a realtime provider based on one impressive run. Repeat ambiguous scenarios, include at least one interruption and one recovery test, and compare against the same rubric.
- Do not classify missing `sophia.artifact` as merely a voice-quality issue. For companion turns it is event-contract evidence and should affect the event correctness/tool integration score.
- Do not treat Gemini `serverContent.interrupted` as a backend-only diagnostic. Browser playback owns the queued PCM audio and must stop/clear it immediately when the provider reports interruption.
- Do not treat stopping active Web Audio sources as a complete Gemini barge-in fix. Playback flushes need a generation/stale-output fence so later chunks from the interrupted assistant response cannot be scheduled after the user starts talking.
- Do not reset assistant transcript stale guards on Gemini interruption. Mark the active response/segment interrupted and keep enough state to reject later stale fragments with higher source sequences.
- Do not allow public assistant transcript from a closed/interrupted response to mutate the active transcript just because its source sequence is newer than the interruption event. Closed response ids are terminal until an explicit new provider response start reopens that id.
- Do not count raw Gemini `emit_artifact` tool calls as public artifacts during interruption/cancellation analysis. Artifact success still comes from validated `sophia.artifact` events and rendered/runtime artifact state.
- Do not display every Gemini `outputTranscription` partial as a live Session message. Google documents transcription as independent of audio timing; Gemini production partials should be paced after safe assembly and final text should remain exact.
- Do not treat Gemini `serverContent.outputTranscription.text` as guaranteed cumulative snapshots or as safe-to-drop raw partials. The Phase 12.4K live smoke showed delta-like fragments; relay every raw fragment in source order unless an app-owned assembler has first produced a cumulative local snapshot.
- Do not treat Gemini `serverContent.outputTranscription.text` as guaranteed append-only deltas either. The backend normalizer must assemble unknown chunks into replaceable public snapshots with duplicate, overlap, revision, and whitespace handling.
- Do not assume residual Gemini transcript corruption is always another text-merge heuristic bug. If clean provider fragments are applied out of provider order, a correct-looking append fallback can still create phrases such as `to lock You ready` or `tell I can't It has you`.
- Do not treat browser-local Gemini correlation ids as an ordering contract unless the provider receive sequence is carried through relay, backend mapping, public emission, and Session ingestion.
- Do not use raw provider receive sequence alone as a contiguous backend reorder key when some Gemini messages are local-only. Carry a separate relayed-message sequence so skipped audio/setup-adjacent frames do not leave permanent ordering gaps.
- Do not assign Gemini `provider_relay_sequence` before an event is actually sent. Only sent events can participate in the backend's contiguous relay sequence.
- Do not coalesce final Gemini assistant transcript boundaries, raw assistant output transcription, user input transcription, tool calls, tool-call cancellations, interruptions, setup/lifecycle messages, errors, or turn boundaries. Raw non-final assistant `outputTranscription` fragments are non-droppable until a source-ordered local cumulative assembler exists.
- Do not mutate Gemini transcript buffers from a provider event that is older than the latest source sequence for that response/segment. Emit a compact diagnostic and ignore the stale snapshot instead.
- Do not treat Phase 12.4G-B transcript source ordering as proof that Gemini native audio is ordered. Pure `modelTurnAudio` chunks are browser-local, so they need their own receive sequence, compact chunk hash, byte length, decode timing, and scheduled-start ledger.
- Do not debug bad Gemini speech from transcript evidence alone. A malformed visible transcript can be public-event ordering, while malformed native audio can be provider output, browser PCM scheduling, duplicate chunks, stale post-interruption scheduling, or a mixed cause.
